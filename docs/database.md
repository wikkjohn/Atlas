# Database

PostgreSQL 16 is the single system of record. All schema changes are Alembic migrations in
`backend/alembic/versions/`; tables are never created implicitly at application start.

## Conventions

- Constraint and index names follow the naming convention in `app/core/database.py`, so
  autogenerated migrations are deterministic.
- Timestamps are `timestamptz` and stored in UTC.
- Money will be stored as integer minor units (`bigint`) with an ISO 4217 currency
  column. Floating-point types are never used for balances.
- `tests/test_migrations.py` fails when models and migrations differ.

## Migrations

| Revision | Phase | Description |
| --- | --- | --- |
| `0001_platform_baseline` | 1 | Creates `system_properties`; records `platform.initialized_at` |
| `0002_enterprise_foundation` | 2 | Countries, organizations, roles, users, employees, audit events (with append-only triggers), idempotency keys, `employee_number_seq`; seeds the 8 roles and 5 initial countries |
| `0003_banking_core` | 3 | Customers, account requests, accounts, ledger accounts, journal entries and lines; customer/account/journal number sequences; ledger balance and immutability triggers |
| `0004_workflow_engine` | 4 | Workflow definitions (snapshots), executions, step runs, append-only workflow events; customer notifications |
| `0005_simulation_engine` | 5 | Simulation runs and per-case results; `workflow_executions.simulation_run_id` |
| `0006_ai_innovation_lab` | 6 | AI tools and invocations; run mode, tool and suite; the `automated_policy` role and the policy-engine service account |
| `0007_experiments` | 7 | Experiments, raw measurements and derived evaluations |
| `0008_payments_lending` | 9 | Payments and loans; `payment_number_seq`, `loan_number_seq` |

Common commands (from `backend/`):

```bash
.venv/bin/alembic upgrade head                           # apply all migrations
.venv/bin/alembic current                                # show the applied revision
.venv/bin/alembic downgrade -1                           # roll back one revision
.venv/bin/alembic revision --autogenerate -m "message"   # draft a new migration (review it!)
.venv/bin/alembic check                                  # fail if models need a migration
```

## Tables

### `system_properties` (Phase 1)

Key/value facts about this installation.

| Column | Type | Notes |
| --- | --- | --- |
| `key` | `varchar(100)` | Primary key |
| `value` | `text` | Not null |
| `updated_at` | `timestamptz` | Defaults to `now()` |

Seeded rows: `platform.initialized_at`, the UTC time the baseline migration ran.

### `countries` (Phase 2)

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `uuid` | PK |
| `iso_country_code` | `varchar(2)` | Unique; CHECK `^[A-Z]{2}$` |
| `country_name` | `varchar(100)` | Unique |
| `region` | `varchar(30)` | CHECK in americas, europe, middle_east_africa, asia_pacific |
| `default_currency` | `varchar(3)` | CHECK `^[A-Z]{3}$` (ISO 4217) |
| `default_timezone` | `varchar(64)` | IANA name (validated by the API) |
| `supported_languages` | `varchar(16)[]` | Language tags |
| `operational_status` | `varchar(20)` | CHECK in active, planned, suspended |
| `created_at`, `updated_at` | `timestamptz` | |

Seeded: US, GB, DE, SG, JP (all active). The schema has no country limit; the 120-country
target is exercised by a test.

### `organizations` (Phase 2)

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `uuid` | PK |
| `name` | `varchar(200)` | Unique among siblings |
| `organization_type` | `varchar(30)` | global_bank, regional_headquarters, country_subsidiary, business_division, department, team |
| `parent_organization_id` | `uuid` | FK → organizations; NULL only for the global bank (CHECK) |
| `country_id` | `uuid` | FK → countries; set from the subsidiary downward |
| `region` | `varchar(30)` | Set from the regional headquarters downward |
| `status` | `varchar(20)` | active, inactive |
| `created_at`, `updated_at` | `timestamptz` | |

Partial unique indexes: one `global_bank`; one `country_subsidiary` per country.

### `roles` (Phase 2)

`id`, `code` (unique), `name`, `description`. The permissions of each role are defined in
`app/core/permissions.py`.

### `users` (Phase 2)

`id`, `username` (unique, lowercase), `email` (unique), `display_name`, `password_hash`
(salted scrypt), `role_id` → roles, `employee_id` → employees (unique, optional),
`is_active`, `last_login_at`, timestamps. Users are deactivated, never deleted.

### `employees` (Phase 2)

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `uuid` | PK |
| `employee_number` | `varchar(20)` | Unique; `AGB-` + `employee_number_seq` |
| `first_name`, `last_name` | `varchar(100)` | |
| `email` | `varchar(254)` | Unique; synthetic `@atlasbank.example` |
| `organization_id` | `uuid` | FK → organizations (a department or team) |
| `department_id` | `uuid` | FK → organizations (derived) |
| `manager_id` | `uuid` | FK → employees; CHECK not self; cycles prevented by the service |
| `job_title` | `varchar(150)` | |
| `role_id` | `uuid` | FK → roles (default platform role for a user account) |
| `country_id` | `uuid` | FK → countries |
| `employment_status` | `varchar(20)` | active, on_leave, terminated |
| `annual_compensation` | `bigint` | Minor units; CHECK ≥ 0 |
| `compensation_currency` | `varchar(3)` | From the country's default currency |
| `created_at`, `updated_at` | `timestamptz` | |

### `audit_events` (Phase 2)

`id`, `actor_id` → users (NULL for system actions), `action`, `entity_type`, `entity_id`,
`timestamp`, `correlation_id`, `metadata` (jsonb). Indexed by entity, timestamp, actor and
action. Triggers `audit_events_no_update_delete` and `audit_events_no_truncate` raise
`insufficient_privilege` on any modification.

### `idempotency_keys` (Phase 2)

PK (`actor_id`, `key`); `method`, `path`, `request_hash` (SHA-256 of method, path and body),
`status_code`, `response_body` (jsonb), `created_at`. Expired keys are not yet pruned.

### `customers` (Phase 3)

`id`, `customer_number` (unique, `CUS-` + sequence), `customer_type` (individual,
business), `name`, `date_of_birth_or_incorporation` (date), `country_id` → countries,
`risk_rating` (unrated, low, medium, high), `kyc_status` (not_started, pending, verified,
rejected), timestamps. KYC transitions are enforced by the service.

### `account_requests` (Phase 3)

`id`, `customer_id`, `account_type`, `currency`, `status` (pending, approved, rejected),
`requested_by` / `decided_by` → users, `decided_at`, `decision_note`, `account_id` →
accounts (unique), timestamps. CHECKs: `decided_by <> requested_by` (four-eyes);
approved ⇔ `account_id` set. Partial unique index: one pending request per customer,
type and currency.

### `accounts` (Phase 3)

`id`, `account_number` (unique; country + 10 digits + MOD 97-10 check digits),
`customer_id`, `account_type` (current, savings, business_current), `currency`, `status`
(open, frozen, closed), `ledger_account_id` → ledger_accounts (unique), `opened_at`,
`closed_at` (set iff closed). Partial unique index: one non-closed account per customer,
type and currency. **No balance column** — balances come from the ledger.

### `ledger_accounts` (Phase 3)

`id`, `code` (unique, e.g. `1000-USD` cash, `2100-<account number>` customer deposits),
`name`, `account_type` (asset, liability, equity, income, expense), `currency`,
`created_at`. Assets and expenses are debit-normal; the rest credit-normal.

### `journal_entries` (Phase 3)

`id`, `entry_number` (unique, `JE-` + sequence), `idempotency_key` (unique), `request_hash`,
`currency`, `description`, `source` (manual, deposit, withdrawal, reversal), `status`
(posted, reversed), `effective_date`, `posted_at`, `posted_by` → users, `correlation_id`,
`reversal_of_id` → journal_entries (unique).

### `journal_lines` (Phase 3)

`id`, `journal_entry_id`, `line_number` (unique per entry), `ledger_account_id`,
`direction` (debit, credit), `amount` (bigint minor units, CHECK `0 < amount ≤ 10^15`),
`memo`.

Ledger triggers (migration 0003):

| Trigger | Rule |
| --- | --- |
| `journal_lines_balanced`, `journal_entries_balanced` (deferred constraint triggers) | An entry has ≥ 2 lines, debits = credits, and every line's account is in the entry's currency |
| `journal_lines_no_update_delete`, `journal_lines_no_truncate` | Lines are immutable |
| `journal_lines_insert_with_entry` | Lines can only be added in the transaction that posted the entry |
| `journal_entries_guard`, `journal_entries_no_truncate` | Entries cannot be deleted; the only permitted update is status posted → reversed |

### Workflow tables (Phase 4)

| Table | Contents |
| --- | --- |
| `workflow_definitions` | Snapshot of each definition version used: `workflow_id`, `version` (unique together), `definition` (jsonb), `content_hash` |
| `workflow_executions` | `workflow_id`, `workflow_version`, `definition_id`, `status` (running, waiting, completed, failed, cancelled), `outcome`, `current_steps`, `context` (jsonb), `error`, `business_key`, `initiated_by`, `idempotency_key` (unique per initiator), `correlation_id`, `started_at`, `completed_at`, `step_counter` |
| `workflow_step_runs` | One row per step visit: `sequence` (unique per execution), `step_id`, `step_type`, `status` (pending, waiting, completed, failed, cancelled), `branch`, `attempt`, `required_permissions`, `actor_id`, `output`, `error`, `created_at`, `started_at`, `completed_at`, `duration_ms`, `not_before` (retry), `due_at` (timeout), `escalated_at`. Partial indexes for due pending runs and waiting timers. |
| `workflow_events` | Append-only history (`seq` identity, `event_type`, `occurred_at`, `actor_id`, `data`); triggers reject UPDATE, DELETE, TRUNCATE |
| `customer_notifications` | Simulated messages (`customer_id`, `channel`, `subject`, `body`, `workflow_execution_id`) |

`workflow_executions.simulation_run_id` (Phase 5, nullable, indexed) links executions a

### Payments and lending tables (Phase 9)

| Table | Contents |
| --- | --- |
| `payments` | `payment_number` (`PAY-…`), `debtor_account_id`, `creditor_account_id` (distinct, → `accounts`), `amount` (minor units, > 0), `currency`, `reference`, `status` (pending, released, rejected), `initiated_by`, `approved_by` (CHECK ≠ `initiated_by`), `journal_entry_id` (set exactly when released; unique), `rejection_reason`, `workflow_execution_id`, `created_at` (business time), `decided_at` |
| `loans` | `loan_number` (`LN-…`), `customer_id`, `disbursement_account_id`, `ledger_account_id` (the loan receivable, an asset; unique), `principal`, `currency`, `annual_rate_bps`, `term_months` (6–84), `monthly_payment`, `purpose`, `status` (active, repaid, written_off; Phase 10), `requested_by`, `underwritten_by` (CHECK ≠ requester), `committee_approved_by` (CHECK ≠ requester and underwriter), `disbursement_entry_id` (unique), `workflow_execution_id`, `disbursed_at`, `created_at` |

Balances are still never stored: a loan's outstanding amount is the balance of its
receivable ledger account (`1300-LN-…`).

### Loan servicing tables (Phase 10, migration `0009_loan_servicing`)

| Table | Contents |
| --- | --- |
| `loans` (new columns) | `interest_receivable_account_id` (→ `ledger_accounts`, `1310-LN-…`, unique), `closed_on` (business date), `closed_at`, `written_off_by` (→ `users`), `write_off_entry_id` (→ `journal_entries`, unique). CHECK `closed_has_date`: a loan is active exactly when `closed_at` is null |
| `loan_instalments` | `loan_id` (cascade), `number` (unique per loan), `due_date`, `principal`, `interest` (minor units, ≥ 0), `status` (scheduled, due, paid, prepaid, written_off), `accrual_entry_id`, `payment_entry_id`, `paid_on`. CHECK `entries_match_status`: each status has exactly the postings it implies (e.g. `paid` ⇒ accrual and payment entries, `scheduled` ⇒ neither) |
| `loan_servicing_runs` | `run_number` (identity), `as_of` (the business date serviced to), `started_by`, `summary` (jsonb: loans, accrued, collected, missed, repaid, in arrears, arrears per currency, buckets), `created_at` |

The **lending business date** is the latest `loan_servicing_runs.as_of`; it never moves
backwards. The migration backfills a schedule and an interest receivable for every
existing loan (a frozen copy of the schedule maths), and widens
`workflow_step_runs.duration_ms` to BIGINT because a collections case can wait for months. Downgrading
0009 drops the instalments and servicing runs (their ledger postings stay); upgrading again
rebuilds every schedule as unpaid, so do not service a downgraded-and-upgraded book.

Ledger accounts used by servicing: `1300-LN-…` loan receivable, `1310-LN-…` interest
receivable (per loan), `4100-<CUR>` interest income, `5100-<CUR>` loan losses.
